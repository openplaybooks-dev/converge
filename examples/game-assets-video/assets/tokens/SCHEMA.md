# Tokens Schema

This is the **file format reference** for the tokens library. It documents
required fields, valid enums, validation rules, and the compiled-output
shape. For the principles behind the format — what a token is, how
categories partition the design space, when to fork width-variants,
the sketch contract — see `TOKENS_SPEC.md` next door.

> SCHEMA = what fields, what enums, what the compiler validates.
> SPEC   = why each field exists and how to fill it well.

A tokens library is a per-game token set. Each token is a named, reusable
visual element with three things:

- a **body** — its footprint and anchor (how it occupies space)
- a **sketch** — a small image showing what it looks like (rough)
- **visual attributes** — color, material, layer eligibility, art notes

Building a game = defining a tokens library + mapping tokens into scenes.
Image generation paints over the token assembly to produce the final
visuals.

---

## Directory layout

```
assets/tokens/
├── SCHEMA.md                          # this file
├── TOKENS_SPEC.md                     # principles for authoring
├── ASSEMBLY.md                        # scene-assembly format
└── {biome}/                           # one folder per biome
    ├── index.json                     # compiled token index for this biome
    ├── ground/                        # category=ground tokens
    │   └── {token-id}/                # per-asset folder
    │       ├── token.md               # frontmatter spec (authored)
    │       ├── token.json             # compiled (generated)
    │       ├── concept.png            # painted concept image (generated)
    │       ├── prompt.txt             # AI prompt (generated)
    │       └── seed.txt               # generation seed (generated)
    ├── platforms/                     # category=platform tokens
    ├── hazards/                       # category=hazard tokens
    ├── decorations/                   # category=decoration tokens
    ├── background/                    # category=background tokens
    └── markers/                       # category=marker tokens
```

Tokens are biome-scoped because the same logical token (e.g. "ground")
looks different in grassland vs cave vs ice — each biome has its own
sketch even if the gameplay contract is identical.

Within a biome, tokens are split into six **category folders**, one per
value of the `category` enum (pluralised for readability). The compiler
requires that a token file's directory match its frontmatter `category`:

| `category` value | required folder name |
|---|---|
| `ground` | `ground/` |
| `platform` | `platforms/` |
| `hazard` | `hazards/` |
| `decoration` | `decorations/` |
| `background` | `background/` |
| `marker` | `markers/` |

## Token definition file

A markdown file with YAML frontmatter. The token's sketch lives next
to `token.md` inside the per-asset folder; the painted concept lives
sibling to it as `concept.png`.

```markdown
---
id: pond                          # unique within the biome
biome: grassland
category: hazard                  # ground | hazard | platform | decoration | background | marker
kind: terrain                     # terrain (static, painted once) | dynamic (engine-driven sprite)
body:
  footprint: { width: 6, height: 2 }    # in concept-tile units
  anchor: bottom-left                    # where (at_tile) places the token: bottom-left | top-left | center
layers: [play]                    # which layers this token can be placed in
gameplay:
  passable: false
  damage: 1
  beats: [hazard]
visual:
  symbol: "W"                     # single-char symbol for this token on layer ASCII grids
  fill: "#3A6FAA"                 # primary color (used when sketch falls back to flat color)
  material: "wetland water"
  detail_density: low             # low | medium | high — how much detail the painter should add
  art_notes: |
    A small wetland pond with grass shoreline. Reeds and lily pads
    in the interior, soft mud bank where water meets grass.
sketch:
  file: concept.png               # sibling to this token.md inside the per-asset folder; generated by scripts/generate_token_concepts.py
  size_px: [1024, 341]            # PNG dims: long side = 1024, short side scaled by footprint aspect
---
```

### Field meanings

| field | type | meaning |
|---|---|---|
| `id` | string | unique within biome |
| `biome` | string | folder name |
| `category` | enum | semantic category — drives grouping in the LLM prompt AND determines the on-disk subfolder |
| `kind` | enum | `terrain` (static — painted into the level once at load time; lives on a sub-layer's grid) or `dynamic` (engine-driven — sprite spawned at the token's `at` coord; lives in a sub-layer's `# props` YAML block, never on a grid). Default: `terrain`. |
| `body.footprint` | `{width, height}` | size in **concept-tile units** (not pixels). Concept-tile size is per-game, set in `assets/game.json`. |
| `body.anchor` | enum | which corner of the footprint the token's `at_tile` coordinate refers to. Defaults to `bottom-left`. |
| `layers` | string[] | which layers this token is allowed in. The same token id can be eligible for multiple layers (e.g. `tree-cluster` in `bg-mid` and `fg`). |
| `gameplay` | object | gameplay contract: passable, damage, beats. Only meaningful when the token lives in a gameplay layer. |
| `visual.symbol` | string (1 char) | single ASCII char this token projects to on layer-mapping grids (`mappings/{layer}.md`). Required. Layer-scoped uniqueness: no two tokens eligible for the same layer can share a symbol. Reserved chars: `.` (empty cell), space, backtick. See TOKENS_SPEC.md §10 for symbol design heuristics. |
| `visual.fill` | hex | fallback color when the sketch is missing or being run flat. |
| `visual.material` | string | short text the painter sees as guidance |
| `visual.detail_density` | enum | low/medium/high — controls how much detail the painter adds inside the token's footprint |
| `visual.art_notes` | string | free-form painter guidance, flows into the per-token line of the layer prompt |
| `sketch.file` | path | the token's painted concept PNG (rendered by `generate_token_concepts.py`) |
| `sketch.size_px` | `[w, h]` | PNG dimensions; long side = 1024, short side scaled by footprint aspect |

### What's deliberately NOT in the token

- **Tile-map / collision tile codes.** The play-layer collision grid
  is derived from token footprints + their `gameplay.passable` field.
  No more single-char tile-code grids per token.
- **Skeleton-kinds grid.** The sketch IS the skeleton. No separate
  symbolic grid.
- **Connection rules.** The composer warns on weird placements
  (a pond floating in the sky) by checking `layers` eligibility +
  basic adjacency, but rich connection rules are deferred until
  proven necessary.

## Concept image (`{token-id}/concept.png`, sibling to `token.md`)

A painted PNG showing the token in the project's target style.
Generated by `scripts/generate_token_concepts.py` from the token's
frontmatter (id, footprint, visual.fill, material, art_notes) plus
the biome's landscape concept and project style anchors. The PNG
replaces the older hand-drawn SVG sketch — the painter sees painted
content from the start instead of a flat-vector starting point.

The concept image's role is to give the stamper a paintable visual
that, once stamped into per-layer maps, the scene painter can refine
into finished art without fighting an off-style starting state.

### Constraints

A concept image must:

- Be a `.png` with an alpha channel (`RGBA` or `LA` mode). Transparent
  background; the token's silhouette occupies the canvas.
- Match `sketch.size_px` within ±2 px in each dimension.
- Have aspect ratio matching `footprint.width / footprint.height`
  within 5%. The compiler enforces this — a 6×2 pond's PNG must read
  wide-and-short, not square.
- Long side = 1024 px by convention; short side scales by footprint
  aspect. A 1×1 marker → 1024×1024; a 5×1 ground → 1024×205; a 4×6
  branch-frame → 683×1024. Short side is floored at 256 px so very
  thin strips remain legible.

The constraint is enforced by `scripts/tokens_compile.py`. SVG
sketches are no longer supported and the compiler rejects them.

## Compiled index (`index.json`)

The compiler walks `tokens/{biome}/**/*.md` recursively, validates each
token's PNG concept image, and writes
`assets/tokens/{biome}/index.json`:

```json
{
  "biome": "grassland",
  "tokens": [
    {
      "id": "pond",
      "category": "hazard",
      "footprint": [6, 2],
      "layers": ["play"],
      "sketch_png": "tokens/grassland/hazards/pond.sketch.png",
      "source": "tokens/grassland/hazards/pond.md"
    }
  ]
}
```

`source` paths reflect the token's category subfolder.

## Validation

The compiler checks:

1. Frontmatter is valid YAML, has required keys (id, biome, category,
   body.footprint, layers, visual.symbol, sketch.file). `kind` is
   optional and defaults to `terrain`.
2. `body.footprint.width × body.footprint.height` are positive integers.
3. `layers` references known layer ids (currently: `bg-far`, `bg-mid`,
   `play`, `fg`).
4. `category` is in the allowed enum.
5. **Category-folder match:** the token's MD file lives directly in
   `tokens/{biome}/{category-folder}/` where `{category-folder}` is the
   pluralised folder name for its `category` value (see Directory layout
   table). A `category: hazard` token in `assets/tokens/grassland/decorations/`
   is rejected.
6. `visual.symbol` is exactly one character, not in the reserved set
   (`.`, space, backtick).
7. **Layer + kind-scoped symbol uniqueness:** for each `(parallax_layer,
   kind)` pair, no two tokens may declare the same symbol. Two tokens
   on different layers may share a symbol; two tokens on the same
   layer with different `kind` values may also share a symbol (terrain
   and dynamic live in different sub-layer files, so their symbol
   spaces are independent).
8. `sketch.file` resolves to an existing `.png` next to the MD.
9. `id` is unique within the biome.
10. The PNG opens cleanly via Pillow.
11. **Concept image dimensions:** PNG dimensions match `sketch.size_px`
    (±2 px tolerance for generator drift), and `sketch.size_px` aspect
    ratio matches `footprint` aspect within 5%.
12. **Alpha channel:** PNG mode is `RGBA` or `LA` — the token's
    silhouette must sit on a transparent background so the painter's
    layer composition works correctly.

The compiler also emits a per-`(layer, kind)` reverse index in
`assets/tokens/{biome}/index.json::by_layer_kind`:

```json
{
  "by_layer_kind": {
    "bg-far": {
      "terrain": { "M": "mountain-distant", "m": "mountain-small", "~": "tree-band-far" }
    },
    "bg-mid": {
      "terrain": { "T": "tree-cluster-mid", "t": "tree-cluster-near", "b": "bush" }
    },
    "play": {
      "terrain": { "#": "ground", "g": "ground-3w", "G": "ground-10w", "@": "ground-20w" },
      "dynamic": { "S": "spawn", "X": "exit", "K": "pickup-key", "P": "pickup-potion" }
    },
    "fg": {
      "terrain": { "Y": "branch-frame", "t": "tree-cluster-near" }
    }
  }
}
```

The mapping compiler uses this index to look up
`(parallax_layer, kind, symbol) → token_id`. Sub-layer files
declaring `kind: terrain` look up symbols in the terrain table; files
declaring `kind: dynamic` look up token ids directly from a `# props`
YAML block (no grid involved).
